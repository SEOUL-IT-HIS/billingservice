==============================================================================
 billingservice 백엔드 정리 (어노테이션 + 실제로 더 중요한 흐름)
==============================================================================
 - 모든 예시는 이 프로젝트의 실제 코드에서 가져왔다. (파일명 표기)
 - 1~7장: 계층별 어노테이션 / 8~10장: 서비스 구현체 패턴, 타 서비스 REST, Kafka


------------------------------------------------------------------------------
 0. 전체 구조 한눈에 보기
------------------------------------------------------------------------------

  [프론트]  --REST-->  Controller  -->  Service(Impl)  -->  Repository(JPA / MyBatis)  --> Oracle DB
                                           |
                                           |--> BusinessDelegate --REST--> admin, patient 서비스
                                           |--> KakaoPayClient   --REST--> 카카오페이 서버
                                           |--> (이벤트) --Kafka 발행--> 병동
  [검사/병동] --Kafka 구독--> BillingChargeKafkaConsumer --> Service(Impl)  (REST 입구와 같은 service 호출)

  패키지는 기능별(billing / charge / kakaopay / master / inquiry) 로 나누고,
  그 안에서 controller / service / repository / dto / entity 로 다시 나눈다.
  공통 코드는 common (config / exception / response) 에 모아 둔다.


------------------------------------------------------------------------------
 1. Lombok 어노테이션 (거의 모든 계층에 나옴) - 먼저 정리
------------------------------------------------------------------------------

  @Getter / @Setter        필드의 getXxx() / setXxx() 를 컴파일 때 자동 생성
  @Data                    @Getter + @Setter + toString + equals/hashCode 한방에
                           (ApiResponse, PatientDTO 처럼 단순 DTO에 사용)
  @NoArgsConstructor       기본 생성자 new Xxx().  ★빼먹으면 안 되는 이유:
                             - JSON -> 객체 변환(Jackson)이 기본 생성자로 객체를 만든 뒤 set 한다
                             - MyBatis 결과 매핑도 기본 생성자로 만든 뒤 컬럼을 채운다
                             - JPA Entity 는 기본 생성자가 필수
  @AllArgsConstructor      모든 필드를 받는 생성자 (@Builder 와 같이 쓸 때 필요)
  @Builder                 Xxx.builder().a(1).b(2).build() 형태로 객체 생성 (8장 참고)
  @RequiredArgsConstructor ★ final 필드만 받는 생성자 생성 = 생성자 주입(DI)을 자동으로 해줌
  @Slf4j                   log 변수 자동 생성 -> log.info("..{}..", 값) / log.error("..", e)

  [@RequiredArgsConstructor 가 DI 를 하는 원리]
    @Service
    @RequiredArgsConstructor
    public class PaymentServiceImpl {
        private final BillingDetailRepository billingDetailRepository;   // final 이면
        private final PaymentRepository paymentRepository;               // 생성자 파라미터로 자동 포함
    }
    -> 스프링이 빈을 만들 때 생성자 파라미터 타입에 맞는 빈을 찾아 넣어준다.
    -> @Autowired 를 안 써도 된다. (생성자가 1개면 생략 가능)
    -> 직접 쓰면 이렇게 됨. (BillingMasterServiceImpl, BillingMasterController 가 이 방식)
         public BillingMasterController(BillingMasterService s) { this.billingMasterService = s; }
       결과는 같다. 롬복이 대신 써주는 것뿐.
    -> final 이라서 주입 후 바뀌지 않고, 테스트 때 new 로 직접 넣기도 쉽다.

  [주의] @Value 가 붙은 필드(non-final)는 @RequiredArgsConstructor 대상이 아니다.
         스프링이 객체를 만든 뒤 필드에 값을 꽂아준다. (3장 참고)

 2. common
------------------------------------------------------------------------------

 ■ config  (설정 클래스 = "내가 직접 빈을 등록하는 곳")

  @Configuration    "이 클래스는 빈 설정용" 표시. 스프링 시작 시 읽는다.
  @Bean             메서드의 리턴 객체를 스프링 빈으로 등록한다. (메서드 이름 = 빈 이름)
  @Value("${키}")   application.properties 의 값을 읽어 주입
  @ConditionalOnProperty(prefix="app.kafka", name="enabled", havingValue="true", matchIfMissing=true)
                    app.kafka.enabled=true 일 때만 이 클래스/빈을 만든다.
                    matchIfMissing=true : 키가 아예 없으면 켜진 것으로 본다.
                    -> 카프카 서버 없는 로컬에서 false 로 두면 에러 없이 나머지 기능만 테스트 가능.
  @Override         인터페이스/부모 메서드를 구현 (WebConfig 의 addCorsMappings)

  파일별 역할
    RestTemplateConfig   RestTemplate 빈 1개 등록. 연결 3초 / 읽기 5초 타임아웃.
                         -> 타 서비스가 죽어도 무한 대기하지 않고 5초 안에 예외가 난다.
                         -> 이 빈 하나를 PatientBusinessDelegate, AdminBusinessDelegate,
                            KakaoPayClient 가 같이 주입받아 쓴다. (싱글톤)
    WebConfig            CORS 설정 (WebMvcConfigurer 구현).
                         프론트 주소(다른 origin)에서 오는 요청 허용. 허용 목록은
                         app.cors.allowed-origin-patterns 에서 읽음 -> 새 주소가 생기면 코드 말고 설정만 수정.
                         allowCredentials(true) = 쿠키(세션) 포함 요청 허용.
    RedisSessionConfig   로그인 세션을 Redis 에 JSON 으로 저장. 여러 서비스가 세션 공유.
                         SessionUser 를 "kr.co.seoulit.his." 패키지만 역직렬화 허용(보안).
                         그래서 SessionUser 패키지 경로가 모든 서비스에서 같아야 한다.
    KafkaProducer/ConsumerConfig  -> 10장에서 자세히

 ■ exception  (에러를 한 곳에서 일관되게 처리)

  흐름:
    ErrorCode (enum)  : HTTP 상태 + 메시지를 묶어둔 목록   예) BILLING_NOT_FOUND(404, "...")
         |
    BusinessException : ErrorCode 를 들고 있는 RuntimeException.  throw new BusinessException(ErrorCode.X)
         |
    GlobalExceptionHandler : 던져진 예외를 잡아서 ApiResponse 형태의 JSON 으로 응답

  @Getter                      ErrorCode, BusinessException 에서 get 메서드 생성
  @RequiredArgsConstructor     enum 의 final 필드(status, message)를 받는 생성자 자동 생성
  @RestControllerAdvice        "모든 컨트롤러에서 터진 예외를 여기서 처리" (@ControllerAdvice + @ResponseBody)
  @ExceptionHandler(클래스)    어떤 예외를 처리할지 지정
  @Slf4j                       예상 못한 예외의 스택트레이스를 로그로 남김

  핵심 포인트
    - BusinessException 은 RuntimeException 이다 -> @Transactional 이 자동 롤백한다. (7장)
    - 두 단계 핸들러: ① BusinessException -> 의도한 에러(404/409 등)
                      ② Exception -> 예상 못한 에러는 500 + 고정 문구 (내부 정보 노출 방지, 로그는 남김)
    - 스프링은 "더 구체적인 예외 핸들러"를 먼저 고른다.

 ■ response

  ApiResponse<T>   {code, message, data} 로 모든 응답을 통일하는 봉투(envelope).
    @Data @AllArgsConstructor @NoArgsConstructor
    ApiResponse.success(data) / success(message, data) / fail(code, message)
    -> 제네릭 <T> 라서 data 자리에 List<..>, DTO, Void 무엇이든 넣을 수 있다.
    -> 우리 서비스뿐 아니라 admin/patient 도 같은 봉투를 쓴다. 그래서 타 서비스 응답을
       ApiResponse<PatientDTO> 로 받아 getData() 로 꺼낼 수 있다. (9장)
  SuccessCode      성공 메시지 enum (OK, CREATED)


------------------------------------------------------------------------------
 3. controller
------------------------------------------------------------------------------

  @RestController          @Controller + @ResponseBody. 리턴값을 JSON 으로 응답.
  @RequestMapping("/api/billing/payment")   클래스 공통 URL 접두어
  @GetMapping / @PostMapping / @PutMapping / @PatchMapping   HTTP 메서드 + 하위 URL
  @PathVariable            URL 경로의 {값}     /{billingId}        -> String billingId
  @RequestParam            쿼리스트링 ?a=1     (required=false 면 생략 가능)
  @RequestBody             요청 JSON 본문 -> DTO 객체로 변환 (기본 생성자 + setter 필요)
  @Validated               입력 검증 활성화 표시.
                           ※ 지금은 DTO 필드에 @NotNull 같은 검증 어노테이션이 없고 @Valid 도 안 써서
                             사실상 아무 효과가 없는 상태. 검증은 service 에서 if 로 직접 하고 있다.
  Swagger: @Tag(클래스에 그룹명), @Operation(summary, description) -> 문서용일 뿐 동작에 영향 없음

  컨트롤러의 역할 = "받아서 service 에 넘기고, ApiResponse 로 감싸서 돌려주기" 만.
    return ResponseEntity.ok(ApiResponse.success(SuccessCode.OK.getMessage(), result));
    - 비즈니스 로직/검증은 service 에 둔다.
    - ResponseEntity : HTTP 상태코드/헤더까지 제어하는 응답 객체. ok() = 200.

  실제 API 묶음
    BillingDetailController  /api/billing/payment      환자검색, 상세조회, 수납(현금/카드)
    KakaoPayController       /api/billing/payment      ready / approve (같은 접두어 공유)
    BillingChargeController  /api/billing/charge       타 서비스가 REST 로 수납정보 등록
    BillingMasterController  /api/billing/statistics   수납 기준정보(수가) 조회/등록/수정
    BillingHistoryController /api/billing/history      수납이력 조회

  [같은 service 를 부르는 입구가 2개]
    BillingChargeController (REST) 와 BillingChargeKafkaConsumer (Kafka) 가
    둘 다 billingChargeService.createCharge() 를 호출한다.
    -> "입구(전송 방식)만 다르고 로직은 service 하나" 가 계층 구조의 이점.


------------------------------------------------------------------------------
 4. dto / entity
------------------------------------------------------------------------------

 (정리해 둔 목록에서 @Entity/@Table 은 DTO 가 아니라 Entity 쪽 어노테이션)

  DTO     : 계층/서비스 사이로 데이터를 실어 나르는 그릇. DB 와 직접 연결 없음.
            @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder
  Entity  : DB 테이블 한 행과 1:1 로 매핑되는 객체 (JPA 용)
            @Entity                 JPA 가 관리하는 클래스
            @Table(name="BILLING")  매핑할 테이블명
            @Id                     PK
            @Column(name=..., nullable=..., length=..., precision/scale=...)  컬럼 매핑
            @PrePersist / @PreUpdate  INSERT 직전 / UPDATE 직전에 자동 실행
                                    (BillingMasterEntity : createdAt, updatedAt 자동 세팅)
            @Builder.Default        빌더 사용 시에도 필드 기본값 유지 (useYn="Y")

  DTO 종류를 구분하는 습관 (이 프로젝트에 모두 있음)
    요청 DTO    : 프론트/타 서비스 -> 우리    PaymentRequestDTO, BillingChargeRequestDTO
    응답 DTO    : 우리 -> 프론트              BillingDetailResponseDTO, BillingMasterDTO
    조회 결과 DTO: MyBatis 쿼리 결과를 담음    BillingSummaryDTO, BillingDetailItemDTO
    외부 API DTO: 카카오/환자/admin 과 주고받는 모양  KakaoPay...ApiRequestDTO, PatientDTO

  Jackson(JSON) 어노테이션
    @JsonProperty("partner_order_id")   자바 필드는 camelCase, JSON 키는 snake_case 로 맞출 때
                                         -> 카카오페이 API 는 snake_case 를 요구함
    @JsonIgnoreProperties(ignoreUnknown = true)   DTO 에 없는 필드가 JSON 에 와도 에러 내지 않고 무시
                                         -> 타 서비스가 필드를 추가해도 우리가 안 깨지게 하는 안전장치
    @JsonIgnore                          응답 JSON 에서 제외 (BillingDetailItemDTO 의 헤더 반복 필드)

  [요청/응답 변환 방향]
    @RequestBody : JSON  -> DTO   (기본 생성자로 만들고 setter 로 채움)
    return DTO   : DTO   -> JSON  (getter 로 읽음)

  SessionUser : 모든 MSA 서비스가 동일 파일/동일 패키지로 복사해 쓰는 세션 객체. 필드명 변경 금지.


------------------------------------------------------------------------------
 5. repository / mapper : JPA 와 MyBatis 차이  (이 프로젝트는 둘 다 쓴다)
------------------------------------------------------------------------------

                  JPA (Spring Data)                       MyBatis (XML)
  ------------------------------------------------------------------------------------------
  선언            interface X extends JpaRepository       @Mapper interface X  + resources/mapper/X.xml
  SQL             메서드 이름/JPQL 로 자동 생성            XML 에 SQL 을 직접 작성
  대상            Entity 객체                              DTO / Map (아무 모양 결과나 가능)
  잘 맞는 일      단건 조회·저장·수정 (CRUD)               복잡한 JOIN, 윈도우 함수, 프로시저 호출
  이 프로젝트     BillingRepository, PaymentRepository,    BillingDetailRepository,
                  BillingMasterRepository,                 BillingHistoryRepository
                  KakaoPayReadyRepository

 ■ JPA
   - 메서드 이름 규칙으로 쿼리 생성 (구현 없음!)
       findByUseYn("Y")                          -> WHERE use_yn = 'Y'
       findByFeeCode(code)                       -> WHERE fee_code = ?   (Optional 반환)
       findByReceptionIdAndBillingStatus(a, b)   -> WHERE reception_id=? AND billing_status=?
   - 기본 제공: save, saveAndFlush, findById, deleteById, findAll ...
   - @Query         직접 JPQL 작성 (테이블이 아니라 "엔티티 이름/필드명" 기준)
   - @Modifying     SELECT 가 아닌 UPDATE/DELETE 쿼리일 때 필수. clearAutomatically=true 는
                    실행 후 영속성 컨텍스트를 비워 메모리의 옛 값과 DB 가 어긋나지 않게 함.
   - @Lock(PESSIMISTIC_WRITE)  SELECT ... FOR UPDATE. 조회한 행을 트랜잭션 끝날 때까지 잠금.
                    -> KakaoPayReadyRepository.findByIdForUpdate (동시에 approve 두 번 방지, 11장)
   - save vs saveAndFlush
       save()         영속성 컨텍스트에만 담고, DB 반영은 나중(커밋/flush 시점)일 수 있음
       saveAndFlush() 즉시 INSERT/UPDATE 를 DB 로 보냄
     ★ 이 프로젝트에서 saveAndFlush 를 쓰는 이유 2가지
       1) BillingChargeServiceImpl : JPA 로 billing 저장 직후 MyBatis 가 billing_detail 을 INSERT 하는데
          billing 이 아직 DB 에 안 나가 있으면 FK 위반 -> 먼저 flush
       2) BillingMasterServiceImpl : 유니크 제약 위반을 "커밋 시점"이 아니라 그 자리에서 잡아
          try/catch(DataIntegrityViolationException) 로 BusinessException 으로 변환하려고

 ■ MyBatis
   - 인터페이스(@Mapper) + XML 이 이름으로 연결된다.
       XML  <mapper namespace="...BillingDetailRepository">   <- 인터페이스 전체 경로(FQCN)
       XML  <select id="findBillingDetailFull">               <- 메서드 이름과 동일
   - 파라미터 바인딩 #{billingId}  : PreparedStatement 의 ? (SQL 인젝션 안전). ${} 는 문자열 치환이라 지양.
   - 여러 파라미터는 @Param("billingId") 로 이름을 붙인다.
   - resultType : 결과 행을 DTO 로 변환. SQL 에서 AS billingId 로 별칭을 주거나
                  mybatis.configuration.map-underscore-to-camel-case=true (billing_id -> billingId)
   - 동적 SQL  <where>, <if test="...">, <foreach collection="patientIds" open="(" separator="," close=")">
       -> IN 절 만들 때 (환자 ID 목록 검색)
   - 윈도우 함수  SUM(bd.amount) OVER (PARTITION BY b.billing_id)
       -> 상세 항목 행마다 헤더 합계를 반복해서 붙임. service 에서 items.get(0) 으로 헤더를 꺼내는 이유.
   - 프로시저 호출  statementType="CALLABLE"
       {call calc_charge_amount(#{fee_code, mode=IN, ...}, #{unit_price, mode=OUT, ...})}
       -> OUT 값은 반환값이 아니라 "넘겨준 Map 에 채워진다"
            Map<String,Object> p = new HashMap<>(); p.put("fee_code", ..);
            repo.calcChargeAmount(p);  p.get("unit_price");  p.get("amount");
   - 설정  mybatis.mapper-locations=classpath:/mapper/*.xml

 ■ 헷갈리기 쉬운 이름: BillingMasterMapper
   master/mapper/BillingMasterMapper 는 MyBatis 매퍼가 아니다.
   @Component 로 만든 "Entity <-> DTO 변환기"(toDto / toEntity / applyUpdate)다.
   (파일 아래 주석에 MapStruct 라고 적혀 있지만 실제는 직접 짠 변환 클래스)

 ■ 한 서비스 안에서 JPA + MyBatis 를 같이 써도 되는 이유
   둘 다 같은 DataSource/트랜잭션을 쓰기 때문에 @Transactional 한 번으로 묶여 같이 커밋/롤백된다.


------------------------------------------------------------------------------
 6. service
------------------------------------------------------------------------------

  @Service                 비즈니스 로직 계층 빈 등록
  @Transactional           ★ 메서드(또는 클래스 전체)를 하나의 DB 트랜잭션으로 묶는다
  @RequiredArgsConstructor 의존성 주입

  인터페이스(XxxService) + 구현체(XxxServiceImpl) 로 분리
    - 컨트롤러는 인터페이스에만 의존. 구현을 바꿔도 컨트롤러는 영향 없음.
    - 구현 메서드에는 @Override.

  service 가 하는 일 (이 프로젝트 기준)
    1) 입력 검증 (null/공백/범위)  -> 실패 시 throw new BusinessException(ErrorCode.X)
    2) 타 서비스 호출 (환자/공통코드 REST)
    3) 계산 (금액, 본인부담/보험부담)
    4) Repository 로 저장/조회
    5) 결과를 응답 DTO 로 조립 (8장)


------------------------------------------------------------------------------
 7. @Transactional 이 실제로 해주는 것  (이 프로젝트에서 가장 중요한 개념 중 하나)
------------------------------------------------------------------------------

  - 메서드 시작 시 트랜잭션 시작 -> 정상 종료 시 커밋 -> RuntimeException 이 밖으로 나가면 롤백
  - BusinessException 이 RuntimeException 이라 "던지기만 해도 롤백" 된다.
  - 예) PaymentServiceImpl.processPayment : 여러 billing 을 반복 결제하다
        중간에 한 건이라도 예외가 나면 앞에서 처리한 것까지 전부 롤백
  - 예) KakaoPayServiceImpl.approve : tid 삭제(deleteById) 후 카카오 승인 API 가 실패하면
        예외가 위로 올라가며 삭제도 롤백 -> tid 가 살아 있어 재시도 가능 (설계 의도)
  - 읽기만 하는 BillingHistoryServiceImpl 은 @Transactional 이 없다. (필수는 아님)

  주의할 점
    - 같은 클래스 안에서 this.메서드() 로 부르면 트랜잭션 프록시를 안 거친다. (self-invocation)
      PaymentServiceImpl 은 클래스 전체에 @Transactional 을 걸어 이 문제를 피함.
    - 트랜잭션 안에서 외부 REST 호출을 하면 응답이 느릴 때 DB 커넥션을 오래 잡고 있게 된다.
      (HikariCP 풀이 3개뿐이라 특히 조심 -> ORA-12516 방지 주석 참고)
    - 롤백되는 건 DB 만이다. 이미 보낸 카카오페이 승인이나 Kafka 메시지는 되돌릴 수 없다.
      -> 그래서 Kafka 는 커밋 이후에 보낸다 (10장 - AFTER_COMMIT)


------------------------------------------------------------------------------
 8. 서비스 구현체에서 DTO 만들기 - 빌더 / 람다 / 스트림 패턴 모음
------------------------------------------------------------------------------

 (1) 빌더로 응답 DTO 조립   (@Builder 덕분)
       return BillingDetailResponseDTO.builder()
               .billingId(header.getBillingId())
               .patientName(patient.getPatientName())
               .items(items)
               .build();
     - 필드가 많을 때 생성자(순서 헷갈림)보다 이름이 있어 읽기 쉽다.
     - 값 출처가 섞여 있다: 수납 DB(header) + 환자 서비스(patient) + 쿼리 결과(items)
       -> "여러 출처의 데이터를 하나의 응답 DTO 로 합치기" 가 service 의 핵심 일.

 (2) 삼항 연산자로 조건부 값
       .outpatientAmount(header.getReceptionId() != null ? header.getTotalAmount() : 0L)
       .billingType(receptionId != null ? "OUTPATIENT" : "INPATIENT")
     - 접수ID 가 있으면 외래, 없으면 입원 (receptionId 와 admissionId 중 하나만 존재)

 (3) 스트림으로 리스트에서 원하는 값만 뽑기  (stream -> map -> toList)
       List<PatientDTO> patients = ...;
       searchDTO.setPatientIds(
               patients.stream()
                       .map(PatientDTO::getPatientId)   // PatientDTO -> patientId 문자열
                       .toList());                      // List<String>
     - patients.stream()          : 리스트를 흐름(stream)으로 바꿈
     - .map(PatientDTO::getPatientId)  : 각 요소를 변환. "메서드 참조"(::) = (p) -> p.getPatientId() 의 축약
     - .toList()                  : 다시 리스트로
     - .distinct()                : 중복 제거   (summaries 에서 환자ID 중복 제거할 때)
     - .filter(조건)              : 조건에 맞는 것만 남김
     - 일반 for 문으로 바꾸면 3~5줄이 필요한 걸 한 줄로 표현한 것뿐이다.

 (4) 스트림 + Collectors.toMap : 리스트 -> Map (조회용 사전 만들기)
       Map<String, PatientDTO> patientById = patientBusinessDelegate.getPatientsById(patientIds).stream()
               .collect(Collectors.toMap(PatientDTO::getPatientId, Function.identity()));
     - key = patientId, value = PatientDTO 자신 (Function.identity() = x -> x)
     - 왜 만드나: 아래에서 환자별로 O(1) 로 꺼내려고 (리스트를 매번 뒤지지 않음)
     - 주의: key 가 중복되면 IllegalStateException. 아래처럼 "중복 시 규칙"을 줄 수 있다.
       (BillingDetailServiceImpl.getPatientBillingDetails)
       Collectors.toMap(BillingDetailItemDTO::getBillingId, Function.identity(),
                        (first, ignored) -> first,     // 같은 key 면 먼저 것을 유지
                        LinkedHashMap::new)            // 입력 순서를 유지하는 Map 으로
       -> "billing 별 첫 행(헤더)만 모으기"

 (5) forEach 람다로 "목록에 환자 정보 채워 넣기"   (BillingDetailServiceImpl, BillingHistoryServiceImpl)
       summaries.forEach(summary -> {
           PatientDTO patient = patientById.get(summary.getPatientId());
           if (patient != null) {
               summary.setPatientName(patient.getPatientName());
               ...
           }
       });
     - 수납 DB 에는 환자 이름이 없다 (환자 서비스 소유 데이터).
       그래서 ① DB 에서 patientId 목록 조회 ② 환자 서비스에서 이름 등 조회 ③ patientId 로 매칭해 채움
       = MSA 에서 JOIN 대신 쓰는 "애플리케이션 조인" 패턴
     - 람다 (summary -> {...}) : "각 summary 에 대해 이 블록을 실행" 하는 이름 없는 함수
     - null 체크: 환자 서비스에서 못 찾은 환자는 이름 없이 그대로 두려는 의도

 (6) 스트림 집계  mapToLong + sum
       long outpatientAmount = headerByBillingId.values().stream()
               .filter(h -> h.getReceptionId() != null)
               .mapToLong(BillingDetailItemDTO::getTotalAmount)
               .sum();
     - 외래 건만 걸러서 금액 합계. 입원도 같은 방식으로 합산 -> 총합.
     - 행마다 totalAmount 가 반복돼 있어서 "billing 별 첫 행만" 모은 뒤(4번) 더해야 중복 합산이 안 된다.

 (7) Optional : "값이 없을 수도 있음" 을 다루는 법
       billingMasterRepository.findByFeeCode(code)
               .orElseThrow(() -> new BusinessException(ErrorCode.BILLING_FEE_CODE_NOT_FOUND));
     - Optional<T> 를 반환받아 있으면 꺼내고, 없으면 예외 (람다는 "없을 때 만들 예외").
       billingRepository.findBy...().orElse(null)  -> 없으면 null 로 받아서 새로 만드는 분기에 사용
     - Optional 체이닝:  .map(KakaoPayReadyEntity::getTid).orElseThrow(...)
       "있으면 tid 만 꺼내고, 없으면 예외"

 (8) Entity <-> DTO 변환
       DTO -> Entity : billingMasterMapper.toEntity(dto)   (저장 직전)
       Entity -> DTO : billingMasterMapper.toDto(entity)   (응답 직전)
     - Entity 를 컨트롤러 밖으로 직접 내보내지 않는다 (DB 구조가 외부에 노출되고 변경에 약해짐)
     - 금액은 DTO 에서는 String, Entity 에서는 BigDecimal 로 변환 (BigDecimal 로 돈 계산: 오차 방지)

 (9) BigDecimal 계산  (BillingChargeServiceImpl)
       patientAmount   = amount.multiply(new BigDecimal("0.30"));      // 본인부담 30%
       insuranceAmount = amount.subtract(patientAmount);               // 나머지 = 보험부담
     - 돈은 double 이 아니라 BigDecimal. 문자열로 생성해야 정확하다 (new BigDecimal("0.30")).
     - 보험부담을 "70% 곱셈" 대신 "전체 - 본인부담" 으로 구해 합계가 반올림 때문에 어긋나지 않게 함.

 (10) 영수증번호 재시도 루프  (PaymentServiceImpl)
     - RECEIPT_NO 는 UNIQUE. 랜덤값이 겹쳐 DataIntegrityViolationException 이 나면
       최대 5번까지 새로 뽑아 재시도, 5번 다 실패하면 BusinessException.
     - 여기서도 saveAndFlush 를 써야 그 자리에서 예외가 난다.

 (11) 방어적 검증 : 클라이언트 값은 믿지 않는다
     - 금액을 프론트에서 받지 않고 DB(findBillingDetailFull) 합계로 다시 계산한다.
     - 수량 -> 단가×수량은 DB 프로시저(calc_charge_amount)로 계산, 호출자가 보낸 amount 는 무시.
     - UPDATE 의 WHERE 에 billing_status='READY' 를 넣고 변경 행 수(updated==0)로 중복 결제를 막는다.
       (낙관적인 방식의 이중 처리 방지)

 9. 타 서비스 REST 호출 (BusinessDelegate 패턴)
------------------------------------------------------------------------------

 ■ 왜 필요한가
   - MSA 규칙: 다른 서비스 DB 를 직접 조회 금지. (환자 정보 = patient 서비스, 공통코드 = admin 서비스)
   - 그래서 HTTP 로 상대 서비스 API 를 호출한다.
   - 이 호출 코드를 service 에 흩어놓지 않고 한 클래스에 모은 것이 BusinessDelegate.
       PatientBusinessDelegate : 환자 이름 검색, 단건 조회, 연락처 조회
       AdminBusinessDelegate   : 공통코드(사용중인 codeId) 검증
     -> service 는 "환자 가져와" 만 부르고 URL/예외/JSON 구조는 모른다.
     -> 상대 API 가 바뀌어도 delegate 한 곳만 고치면 된다.

 ■ 구성 요소
   @Component                 빈 등록 (@Service/@Repository 처럼 역할 구분이 없는 범용 빈)
   RestTemplate               스프링의 HTTP 클라이언트 (RestTemplateConfig 에서 타임아웃 설정해 빈 등록)
   base-url                   properties/환경변수. 쿠버네티스에선 http://patient:8087 같은 서비스 이름.
   @Value 생성자 파라미터      AdminBusinessDelegate 는 생성자 파라미터에 @Value 를 붙여 설정값을 주입
                              (final 필드 + 직접 쓴 생성자. @Value("${키:기본값}") -> 기본값 문법)

 ■ 호출 코드 읽는 법  (PatientBusinessDelegate.getPatientById)
     ResponseEntity<ApiResponse<PatientDTO>> response = restTemplate.exchange(
             patientServiceBaseUrl + "/api/patient/{patientId}",   // URL 템플릿: {patientId} 자리에
             HttpMethod.GET,                                       // GET
             null,                                                 // 요청 본문/헤더 없음
             new ParameterizedTypeReference<ApiResponse<PatientDTO>>() {},   // 응답 타입
             patientId                                             // {patientId} 에 들어갈 값
     );
     ApiResponse<PatientDTO> body = response.getBody();
     PatientDTO patient = body == null ? null : body.getData();    // 봉투를 벗기고 data 만 꺼냄

   ★ ParameterizedTypeReference 가 필요한 이유
       제네릭은 컴파일 후 타입 정보가 사라진다(타입 소거). ApiResponse<PatientDTO>.class 같은 건 없다.
       그래서 익명 클래스 {} 로 "제네릭 타입 정보"를 남겨 Jackson 이 data 를 PatientDTO 로 변환하게 한다.
       (단순 DTO 면 getForObject(url, X.class) 로 충분)
   ★ URL 은 문자열 더하기로 파라미터를 붙이지 말고 {변수}+인자 로 넘기면 인코딩이 안전하다.
   ★ 응답 DTO 에는 @JsonIgnoreProperties(ignoreUnknown=true) 를 붙여 상대 필드 추가에 대비 (CommonCodeDTO)

 ■ 예외 처리 (매우 중요)
   RestTemplate 이 던지는 예외
     RestClientException (부모)
       ├─ HttpStatusCodeException   상대가 4xx / 5xx 로 응답     (KakaoPayClient 에서 별도 처리)
       └─ ResourceAccessException   연결 실패 / 타임아웃 (서버 다운)
   -> catch (RestClientException e) 로 묶어 로그를 남기고 우리 BusinessException 으로 변환
        PATIENT_SERVICE_UNAVAILABLE(503), ADMIN_SERVICE_UNAVAILABLE(503)
      => 프론트는 "서버 오류"가 아니라 "환자 서비스와 통신 불가" 라는 명확한 응답을 받는다.
   -> 로그에 상대방 응답 body 를 남기는 습관 (원인은 body 에 있다: 카카오 -703 등)

 ■ 에러를 삼켜야 하는 경우도 있다 (정책 결정)
   - fillContact : 연락처는 부가정보 -> 실패해도 log.warn 만 하고 계속 진행 (수납 흐름 유지)
   - getPatientsById : 환자 한 명 실패는 건너뛰고, "전부 실패"일 때만 예외를 던짐

 ■ 성능 포인트
   - getPatientsById 는 환자 서비스에 다건 API 가 없어 id 마다 단건 호출을 반복한다 (N+1 호출).
     목록이 커지면 느려진다 -> 환자 서비스에 다건 조회 API 를 요청하는 게 근본 해결.
   - AdminBusinessDelegate 의 캐시:
       Map<String, CachedCodes> cache = new ConcurrentHashMap<>();     // 멀티스레드에서 안전한 Map
       private record CachedCodes(Set<String> codeIds, Instant expiresAt) {}   // 값 묶음용 record
       기본 TTL 300초. 만료 전이면 admin 을 안 부른다. admin 에서 코드를 바꾸면 최대 5분 뒤 반영.
       -> Kafka 메시지가 올 때마다 공통코드를 검증하므로 호출을 줄이려는 목적.

 ■ 쿠버네티스와 연결
   ConfigMap 의 ADMIN_SERVICE_BASE_URL / PATIENT_SERVICE_BASE_URL 환경변수가
   properties 의 admin.service.base-url / patient.service.base-url 을 덮어쓴다.
   (스프링 relaxed binding : 점/하이픈 -> 밑줄, 대문자)

 10. Kafka  (구독 = Consumer / 발행 = Producer)
------------------------------------------------------------------------------

 ■ 기본 개념
   Topic             메시지를 쌓는 게시판 이름     (exam-billing-charge, inpatient-billing-charge, settlement.completed)
   Producer          메시지를 보내는 쪽
   Consumer          메시지를 읽는 쪽
   Consumer Group    같은 groupId(billing-service)의 컨슈머들은 메시지를 "나눠" 읽는다.
                     다른 그룹은 각자 "전체"를 읽는다.
                     -> 같은 그룹으로 Pod 를 여러 개 띄워도 한 메시지는 한 곳에서만 처리된다.
   Offset            그룹이 어디까지 읽었는지 표시. 처리가 끝나면 커밋된다.
   Partition         토픽을 쪼갠 단위. 같은 key 의 메시지는 같은 파티션 -> 순서 보장.
   Broker            Kafka 서버 (spring.kafka.bootstrap-servers 주소)

   REST 와의 차이: REST 는 "지금 응답을 기다림"(동기). Kafka 는 "던져놓고 상대가 나중에 처리"(비동기).
   보내는 서비스(검사/병동)는 수납 서비스가 잠시 죽어 있어도 메시지를 보낼 수 있고,
   수납 서비스가 살아나면 쌓인 걸 읽는다.

 ■ 이 프로젝트의 메시지 흐름
   [검사서비스]  --exam-billing-charge------->  \
   [병동서비스]  --inpatient-billing-charge--->   > billing 구독 -> createCharge() -> billing/billing_detail 저장
   [billing]     --settlement.completed------->  병동 구독 (입원 건 결제 완료 -> 퇴원 처리)

 ■ A. 구독(Consumer)

   1) KafkaConsumerConfig  (@EnableKafka @Configuration @ConditionalOnProperty)
      - 이 스프링부트 버전에서 카프카 자동설정이 안 붙어서 직접 빈을 등록했다는 주석 있음.
      - ConsumerFactory<String,Object>  : 컨슈머를 만드는 공장.
          BOOTSTRAP_SERVERS  브로커 주소
          GROUP_ID           billing-service
          AUTO_OFFSET_RESET = earliest   처음 구독하는 그룹이면 가장 오래된 메시지부터 읽음
          TRUSTED_PACKAGES   JSON -> 객체로 바꿀 때 허용하는 패키지 (보안: charge.dto 만)
          USE_TYPE_INFO_HEADERS = false  보낸 쪽 클래스명(__TypeId__ 헤더)에 의존하지 않음
                                         (서비스마다 패키지/클래스명이 다르므로. 순수 JSON 만 주고받기로 약속)
          ObjectMapper FAIL_ON_UNKNOWN_PROPERTIES = false   모르는 필드가 와도 무시
          ErrorHandlingDeserializer  JSON 이 깨진 메시지가 와도 컨슈머가 무한 실패 루프에 빠지지 않게 감싸줌
      - ConcurrentKafkaListenerContainerFactory : @KafkaListener 가 쓰는 실행 컨테이너.
          setCommonErrorHandler(new DefaultErrorHandler(new FixedBackOff(1000L, 2)))
          -> 처리 중 예외가 나면 1초 간격으로 2번 재시도(최초 1회 + 재시도 2회 = 총 3회 시도),
             그래도 실패하면 로그만 남기고 다음 메시지로 넘어감. (한 메시지 때문에 파티션이 막히는 것 방지)
             별도 DLQ(실패 메시지 보관 토픽)는 없다.

   2) BillingChargeKafkaConsumer  (@Component @Slf4j @RequiredArgsConstructor @ConditionalOnProperty)
      @KafkaListener(
          topics = { "${billing.charge.topic.exam}", "${billing.charge.topic.inpatient}" },   // 2개 토픽 동시 구독
          groupId = "${spring.kafka.consumer.group-id}",
          properties = "spring.json.value.default.type=...BillingChargeRequestDTO"           // 이 DTO 로 변환
      )
      public void consumeBillingCharge(BillingChargeRequestDTO request) { ... }
      - 메시지(JSON)가 오면 이 메서드가 자동 호출된다. 파라미터가 곧 역직렬화된 DTO.
      - 토픽 이름은 properties 에서 읽는다 (${...} 자리표시자) -> 코드를 안 고치고 토픽 변경.
      - 퇴원신청 신호(feeCode = DISCHARGE_REQUEST)는 수가가 아니므로 소비 즉시 무시(return).
      - 그 외에는 REST 와 같은 billingChargeService.createCharge(request) 호출.
      - 메서드 안에서 예외가 나면 위의 DefaultErrorHandler 가 재시도/포기를 결정.
      - createCharge 가 @Transactional 이라 실패하면 DB 는 롤백된 채 재시도된다.

   3) 주의할 점 (알아두면 좋은 것)
      - 메시지는 "최소 한 번(at-least-once)" 전달이 기본. 같은 메시지가 두 번 올 수 있다.
        지금 createCharge 는 중복 방지 키(예: sourceRecordId 중복 체크)가 없어서
        재전송되면 항목이 중복 등록될 수 있다. (필요하면 sourceRecordId 로 멱등 처리 검토)
      - 수신 후 3회 실패하면 해당 메시지는 영영 처리되지 않는다 -> 로그를 꼭 확인.
      - 로컬에서 Kafka 가 없으면 app.kafka.enabled=false.

 ■ B. 발행(Producer)

   1) KafkaProducerConfig
      - ProducerFactory : KEY 는 StringSerializer, VALUE 는 JsonSerializer (객체 -> JSON)
        ADD_TYPE_INFO_HEADERS = false : 구독 쪽 설정과 짝. 클래스명 헤더를 빼서 받는 쪽이 우리 클래스를 몰라도 됨.
      - KafkaTemplate<String,Object> : 발행에 쓰는 도구. kafkaTemplate.send(topic, key, value)

   2) 발행 순서 설계 (SettlementCompletedEvent / SettlementCompletedKafkaPublisher) ★ 중요
      문제: 결제 트랜잭션 안에서 바로 Kafka 로 보내면, 이후 DB 가 롤백돼도 메시지는 이미 나가 있다.
            -> 결제가 안 됐는데 병동에서 퇴원 처리되는 사고.
      해결: 스프링 이벤트 + AFTER_COMMIT

        PaymentServiceImpl (@Transactional 안에서)
            eventPublisher.publishEvent(new SettlementCompletedEvent(admissionId));   // 이벤트만 던짐
                          │
                          ▼   (트랜잭션이 "커밋 성공"한 뒤에만 실행됨)
        SettlementCompletedKafkaPublisher
            @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
            public void publish(SettlementCompletedEvent event) {
                kafkaTemplate.send(topic, event.getAdmissionId(), event)
                        .whenComplete((result, ex) -> { 실패면 log.error / 성공이면 log.info });
            }

      - ApplicationEventPublisher : 스프링 내부 이벤트 발행기 (Kafka 와 무관한 같은 JVM 안의 알림)
      - key = admissionId : 같은 입원 건의 메시지가 같은 파티션으로 가서 순서가 지켜진다.
      - send() 는 비동기라 CompletableFuture 를 리턴 -> whenComplete 람다로 성공/실패 콜백.
      - 외래 건은 admissionId 가 없어서 이벤트 자체를 안 던진다 (if (header.getAdmissionId() != null)).
      - 한계: 커밋 후 발행이 실패하면 결제는 이미 확정이라 재시도 없이 로그만 남는다.
        (완벽히 하려면 Outbox 패턴이 필요하지만, 팀 합의로 로그만 남김 - 코드 주석 참고)

 ■ 설정 키 요약 (application.properties)
     app.kafka.enabled=true
     spring.kafka.bootstrap-servers=...:9092
     spring.kafka.consumer.group-id=billing-service
     billing.charge.topic.exam / billing.charge.topic.inpatient      (구독 토픽)
     billing.settlement.topic.completed                              (발행 토픽)

 11. 카카오페이 (KakaoPayClient + Controller + ServiceImpl)  - 구조만 간결하게
------------------------------------------------------------------------------

 ■ 역할 분담
   KakaoPayController    프론트의 /ready, /approve 요청 받기
   KakaoPayServiceImpl   업무 흐름 (금액 검증, tid 저장/삭제, 결제 확정)
   KakaoPayClient        카카오페이 서버와의 HTTP 통신만 담당 (@Component, RestTemplate 사용)
   KakaoPayReadyEntity   ready~approve 사이에 tid 를 보관하는 테이블(KAKAOPAY_READY)

 ■ 결제 흐름 (사용자 입장)
   ① 프론트 -> POST /api/billing/payment/ready {billingId(s)}
        service : DB 에서 금액 재합산(프론트 값 불신) -> KakaoPayClient.ready() 호출
                  -> 응답의 tid 를 DB 에 저장 -> redirectUrl 을 프론트에 반환
   ② 프론트가 redirectUrl 로 사용자를 카카오 결제창으로 이동 -> 사용자가 결제
   ③ 카카오가 사용자 브라우저를 approval-url 로 리다이렉트(?pg_token=...)
        approval-url 은 ready 때 우리가 넘긴 값. 프론트 주소(쿠버네티스 18090)여야 한다.
   ④ 프론트의 콜백 페이지 -> POST /api/billing/payment/approve {billingId, pgToken}
        service : tid 를 DB 에서 꺼내 삭제 -> KakaoPayClient.approve() -> 성공하면
                  paymentService.processPayment(billingIds, "KAKAO_PAY") 로 기존 결제 확정 로직 재사용

 ■ 핵심 포인트
   - tid 를 메모리가 아닌 DB 에 저장: 서버 재시작/Pod 여러 개여도 안 잃어버림.
   - @Lock(PESSIMISTIC_WRITE) 조회(findByIdForUpdate) + 삭제:
       콜백 페이지 새로고침 등으로 approve 가 동시에 두 번 오면 두 번째는 첫 번째가 끝날 때까지 대기했다가
       tid 가 없다는 결과(KAKAOPAY_TID_NOT_FOUND)를 받아 카카오 승인 API 중복 호출을 막는다.
   - 승인이 카카오에서 거절되면 예외 -> @Transactional 롤백 -> tid 삭제도 되돌아가 재시도 가능.
   - 여러 billing 을 한 번에 결제해도 카카오 주문은 하나: 첫 billingId 를 대표 주문번호로 사용.
     approval-url 에 ?billingId=대표&billingIds=a,b,c 를 붙여 콜백에서 목록을 복원.
   - 헤더 인증:  Authorization: SECRET_KEY {secretKey}    (secretKey 는 환경변수 KAKAOPAY_SECRET_KEY)
   - 카카오 JSON 은 snake_case 라 @JsonProperty 로 필드 이름 매핑. 응답은 ignoreUnknown=true.
   - cid=TC0ONETIME : 카카오 테스트 가맹점 코드 (운영 시 변경).
   - 결제취소(cancel)는 미구현이라 컨트롤러/서비스에 주석 처리 + TODO.
       (approve 때 tid 를 지워서 취소에 쓸 수 없음 -> PAYMENT 에 보관하도록 변경 필요)

 12. 수납 등록 핵심 흐름 한 장 요약  (BillingChargeServiceImpl.createCharge)
------------------------------------------------------------------------------

   입력: 타 서비스가 REST 또는 Kafka 로 BillingChargeRequestDTO 전달
     1) receptionId / admissionId 둘 다 없으면 오류
     2) sourceServiceCode 를 admin 공통코드로 검증 (AdminBusinessDelegate, 캐시)
     3) feeCode 로 billing_master 조회 (JPA findByFeeCode) -> 없으면 오류
     4) 프로시저 calc_charge_amount 로 단가/금액 계산 (MyBatis CALLABLE, OUT 은 Map 으로 받음)
     5) 급여/비급여에 따라 본인부담·보험부담 분리 (비급여=전액 본인, 급여=30/70)
     6) READY 상태 billing 이 있으면 합계에 더하고, 없으면 새 billing 생성 (JPA saveAndFlush)
     7) billing_detail INSERT (MyBatis insertBillingDetail)
   -> 전체가 하나의 @Transactional : 중간에 실패하면 6)7) 모두 롤백

 13. 지금 목록에서 보충하면 좋은 항목 (체크리스트)
------------------------------------------------------------------------------

  [ ] @Component vs @Service vs @Repository vs @Configuration : 모두 "빈 등록"이고 역할 표시만 다름
  [ ] @Transactional 롤백 조건(RuntimeException) / self-invocation 주의
  [ ] JPA save vs saveAndFlush, 영속성 컨텍스트
  [ ] MyBatis #{} 바인딩, 동적 SQL(<if>, <foreach>), CALLABLE 프로시저
  [ ] ApiResponse 봉투 + ErrorCode/BusinessException/GlobalExceptionHandler 한 세트
  [ ] RestTemplate.exchange + ParameterizedTypeReference + 예외 변환
  [ ] 스트림(map / filter / distinct / toList / Collectors.toMap) + 메서드 참조(::)
  [ ] Optional(orElseThrow / orElse)
  [ ] Kafka: Topic / Group / Offset / Partition, @KafkaListener, KafkaTemplate, AFTER_COMMIT
  [ ] 설정 외부화: @Value("${키}") <-> properties <-> 쿠버네티스 환경변수
